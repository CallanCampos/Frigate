# dsd configs and the ROM

The configs in `config/<version>/` describe every module of the ROM for dsd: its sections (`delinks.txt`), symbols
and relocations. They are generated by dsd's analysis and then fixed and named by the scripts below, which record
what they did so that it survives regenerating them.

## Source compiler flags

`config/compiler_flags.toml` records flags for individual game sources under `[file_flags]`, keyed by their
canonical `src/.../*.c` paths. Each entry replaces the default option of the same kind in `configure.py`, as
`-ipa function` replaces `-ipa file`; other defaults stay. Both versions use the same settings. Library sources
keep their compiler and overrides in `lib/<name>/library.toml`.

`configure.source_compiler()` resolves the compiler, effective flags and library membership. Ninja,
`compile_all.py` and the matching helpers use it, so a file's setting applies to the build and its probes.
The probe keeps its existing warning/debug policy and compiler selection: game sources default to all installed
compilers, libraries to their own. Explicit probe options still override the defaults. Objdiff's scratch for a game
source with an override uses its effective flags without Shift JIS input encoding, since contexts are UTF-8.

Add an override only when both versions' original functions, data and relocations support it, then verify the
linked modules and both ROMs. This manifest describes compilation; it does not change dsd's section ranges or
relocations. Changes regenerate both the Ninja configuration and objdiff metadata.

## Dead-stripped code

The game was linked with dead-stripping, so a function nothing called is missing from the ROM, while data it had
pooled with live code, such as its function-local statics in MWCC's shared `.data` and `.rodata` sections, stayed. Our
link can't do the same: it keeps everything with `-nodead`, since dead-stripping would also drop the delinked objects
nothing refers to, and `mwldarm -partial` doesn't strip. `config/deadstrip.toml` lists, under `[deadstrip]`, the
symbols the original link dropped from each source file that needs them. For a listed file, `configure.py` compiles
to `build/<version>/unstripped/<path>.o`, and `tools/build/deadstrip.py` writes the object at the usual path, which
the link, objdiff and the report take. The manifest and the script are implicit inputs of that step, and editing
the manifest regenerates `build.ninja`. Every other file builds as before: the step is opt-in, and each entry is a
flagged exception.

The exception departs from three rules: the listed code is written from another decomp with no asm to check it
against, it has no address to be placed by, and its file is marked complete although that code was never compared.
It is used for `src/system/wipe_sub.c` alone, whose 31 dead wipe handlers and their engines come from pret's
pokeplatinum and pokeheartgold, with the two window readers `wipe_wnd.c` lost with them. Any other entry is another
exception for the maintainer to accept.

The strip drops each listed symbol's section, every allocated section that only dropped code reaches (a static
function, a string, an unpooled static), the exception indices of dropped code, the relocations of what stays (the
debug information) into dropped sections, and undefined symbols only dropped code called. A global the list doesn't
name stays even when only dead code calls it, so list every global the original lost. The strip fails when a listed
symbol isn't defined in the object, shares its section with a global that isn't listed, or is reached from code of
the object that stays. With an empty list it copies the object unchanged. `compiler_probe.py` runs each object it
compiles for a listed file through the same strip, so the dropped functions aren't reported.

The strip sees only its own object, and the linker links a call to a symbol nothing defines through a veneer to
address 0 rather than fail. So `tools/build/check_deadstrip.py`, which every version's build runs after compiling,
matching or not, fails when any other compiled or delinked object refers to a listed symbol, or to a function that
only the dropped code called and that neither the ROM's `symbols.txt` nor any object defines.
`tools/decomp/compile_all.py`, which CI runs without the ROMs, does the strip and the same check on its objects.
Declare the listed functions in their source file, not its header, so that no other file can call them, unless
another file's dropped code calls them, as `wipe_sub.c`'s plane swap calls `wipe_wnd.c`'s window readers.

The data-layout tools read a listed file's layout from the unstripped object: the strip removes local initializers
that MWCC's size sort counted, so `rodata_order.py` (`--from-object`, `--check`) and `rodata_solver.py` take
`build/<version>/unstripped/<path>.o` when given the build's object, and say so.

To add an entry, once the maintainer has accepted the exception, write `"src/path.c" = ["DeadFunc", ...]` and make sure
MWCC emits each listed function: a function nothing calls is emitted only when it is global. The ROM has none of the
listed code, so it can't be checked against the original: the source file says in a comment which functions are
reconstructions, from which reference, and what in them is a guess. Add one only when the file's own data shows the dead
code existed, as objects that only it read, or for a function that another entry's dead code calls, as `wipe_wnd.c`'s
readers. `python3 -m unittest tools.build.test_deadstrip` tests the strip and the check, and CI's Compile workflow runs
it.

## Linker symbols

NitroSDK's code reads a few numbers, such as `SDK_IRQ_STACKSIZE`, as the addresses of symbols that the SDK's linker
script defines, so the ROM has them as plain words in the literal pools that load them, with no relocation. dsd's linker
script defines only `__OVERLAY_COUNT` of them. `config/linker_symbols.toml` gives the others and their values, the same
in both versions: the stack sizes, which `os_interrupt.c`, `os_thread.c`, `os_arena.c` and the startup code `crt0.c`
(`_start`, `func_02004d50` and `func_02004da0`) read, and the start of the DSi's extended main memory arena, which
`os_arena.c` reads. `dsd lcf --symbols config/linker_symbols.toml` defines them after `__OVERLAY_COUNT` as absolute
symbols in the linker script it writes, `build/<version>/arm9.lcf`, which the link (or `--shift`'s padding) takes, as
NitroSDK's template defines them in its own. Another one goes in
the config when a file that reads it is written, with its value read from the pool word in both versions.

## Compiler exception indices

MSL's runtime/register_atexit.c, runtime/console_io.c and runtime/call_static_initializers.c use
`-Cpp_exceptions on` and emit 48 bytes of exception indices in `.exceptix`. These are compiler output with relocations
to their functions, placed before ARM9's ordinary `.rodata`. Analysis originally folded this prefix into `.rodata`;
registering it there makes the runtime precede the game's data owners while code order puts the game first, creating
a link-order cycle. `config_fixes.py split-section-prefix . .rodata .exceptix 0x30 0x0208ee28` restores the distinct
module section in both versions and migrates any wholly contained registered ranges. The operation rejects a split
through an owner's range and preserves the module section's kind and alignment. Each runtime file owns its emitted
`.exceptix` range directly, so the linker keeps the compiler's relocations without a C reconstruction of the indices.

## Fixing the configs

dsd sometimes cannot tell which overlay a relocation points to, because many overlays share addresses. It then lists
every candidate, such as `module:overlays(36,214)`, and the build links to the first one, which gives the right bytes
but the wrong symbol. `tools/decomp/config_fixes.py` fixes such relocations and other mistakes in both versions, and
records them in `config/fixes.txt`:

```sh
.venv/bin/python tools/decomp/config_fixes.py reloc-module overlays/ov004 'overlay(214)' 0x0214f6c0
.venv/bin/python tools/decomp/config_fixes.py overlay-id overlays/ov004 214 0x0214f6bc
```

It also removes relocations and symbols that are not real (`remove-reloc`, `remove-symbol`), and gives a function a
second name with `add-label`. MWCC calls the runtime's 64-bit multiply `_ll_mul` for signed values and `_ull_mul` for
unsigned ones, while the game has one copy of it, so `_ll_mul` is a label on `_ull_mul`. `remove-label` drops a label
again once its function takes the name, as the runtime's functions did when they took its names over swan's. A delinked
object defines the label, but a compiled C file defines one name per function, so a label that code calls at a C
function's start makes the link fail with the label undefined once the file is complete: the label is either a wrong
target (`ReshZekSave_Init`'s call was such a label until its overlay 12 target, `CityState_Init`, was found) or a
routine of a library written in assembly, whose `.s` file defines both (`docs/matching.md`). `add-data`
adds an object that nothing references, such as a global constant that the compiler folds into the code but still emits,
so that the object before it does not seem to run on over it.

Use `remove-orphan-reloc` when a relocation is filed in a module whose sections do not contain its source address.
Give the actual source module explicitly; `.` means ARM9 main. The address is the relocation's **source** in Black 2,
not its destination:

```sh
.venv/bin/python tools/decomp/config_fixes.py remove-orphan-reloc overlays/ov011 --source-module . 0x020050c4
```

This maps the address through the source owner, verifies that each version's address is inside that owner's sections
and outside the recorded module's sections, and checks all relocation files before removing anything. It rejects
multiple entries at the same source. An absent entry is allowed, including when only one version contains the
orphan or when replaying the fix. Relocations elsewhere that point to the same destination are preserved. The saved
record includes the source owner (`remove_orphan_reloc .`), so regeneration uses the same checks. Ordinary
`remove-reloc` continues to map its source through the recorded module.

Every fix resolves its addresses and arguments and validates its text changes for both versions before writing either
version, so a mapping error or a conflicting relocation cannot leave only Black 2 changed. Replay still applies fixes
in order because later fixes can depend on earlier ones.

A label preserves an unresolved caller's name without replacing the function's canonical name. Static-reference checks
consider every name at the destination, including labels, and use the first overlay candidate just as the linker does.
An alias therefore cannot hide a reference to a static function.

`section-start` and `section-end` move one end of a registered source file's section, as an object at a boundary
that turns out to belong to the neighbouring file needs; `add_source_file.py` only adds files. The address may be the
section's end, which a section's last file reaches, its alignment padding included. Recording a boundary again
replaces its earlier record, since fixes replay in address order:

```sh
.venv/bin/python tools/decomp/config_fixes.py section-end overlays/ov310 src/ov310/research_list.c .rodata 0x021a7028
```

`remove-section MODULE FILE SECTION EXPECTED_START` removes a section wrongly attributed to a source file, such as
a label inside another file's heap. It verifies the owner and start in both versions before writing; repeating an
already-applied removal is harmless. The fix is recorded for config regeneration.

A relocation that dsd could not pin to one overlay only links while its symbol is global. When a function becomes
`static` in a decompiled file, check `relocs.txt` of both versions for relocations to its address with several
candidate modules, and fix the ones that belong to another overlay. Field gimmicks, such as gym puzzles, share one load
address, so calls between them are often ambiguous; the gimmick table in ov036 gives each entry's overlay ID, and its
pointers are fixed from it.

## Regenerating configs

After improving dsd's analysis, regenerate the configs of both versions and import the names again:

```sh
.venv/bin/python tools/decomp/regenerate_configs.py path/to/swan
```

This keeps the source files listed in each `delinks.txt`, but loses any other manual changes to the configs. It runs
the following command once per version:

```sh
tools/dsd init --rom-config extract/b2_us/config.yaml --output-path config/b2_us --build-path build/b2_us \
    --allow-unknown-function-calls
```

The fixes in `config/fixes.txt` and the names from swan and `config/names.txt` are applied again afterwards, so only
changes made to the configs by hand are lost.

## DSi specifics

Black 2 is an NDS/DSi hybrid built with the TWL-SDK, which differs from DS-only games in ways the tooling had to learn:

- The ARM9 has no footer. Its autoload list has four words per entry, including a `.sinit` address.
- The ROM has a DSi region with ARM9i/ARM7i programs. The first 0x4000 bytes of ARM9i are encrypted with modcrypt
  (AES-CTR). Extraction decrypts it, and the build re-encrypts it.
- Every 0x400-byte sector of the ROM is covered by a SHA1-HMAC digest, and the header holds SHA1-HMACs of each
  program. The build recomputes all of these.
- The digests of the ARM9 secure area are computed over its encrypted form. Without an ARM7 BIOS the build reuses
  the original values, which stay valid as long as the secure area is unchanged.
- The DSi-only LTD ("limited") module is compressed inside ARM9i and loaded to `0x02700000` in DSi mode. ARM9 main
  calls into it. Extraction splits ARM9i into this module (`dsi/ltd_autoload_0.bin`), and the build links, recompresses
  and reinserts it. It has two code regions, which dsd since v0.12.1-dsi.3 lays out as:
  - `.text`: the module's own ARM code, TwlSDK's DSi libraries.
  - `.rodata`: two COFF images for the DSi's Teak DSP. dsd gives each a byte-array symbol, so that their words are not
    taken for pointers.
  - `.ctor`: the empty static initializer table, a zero, that the autoload list points to.
  - `.ltdmain`, from the next 32-byte boundary: Thumb code that calls main's SDK through linker veneers, such as the
    NDMA functions (`MI_IsNDmaBusy` at `0x02768234`). It seems to be the DSi-only code of main's library files, and
    ends with NitroWiFi WCM's DSi backend (`wcm_dsi.c`), which overlay 11 calls. The section's name is a guess, after
    the SDK's LTDMAIN; C code goes there between `#pragma section LTDMAIN begin` and `end`, after
    `#pragma define_section LTDMAIN ".ltdmain" ".ltdmain.bss" ".ltdmain" abs32 RWX`.
  - `.data` and `.bss`.
- Overlay 169 runs from VRAM, at `0x06898020`. Its code is analyzed like any other overlay's since dsd v0.12.1-dsi.3;
  before, dsd took a branch outside main memory for data and had all of it as `.rodata`.

## Long-branch veneers

A call out of `bl` range, such as from an overlay to overlay 169 or the LTD module, goes through a veneer the linker
adds after the calling function. The original shares main's veneers among their callers, but gives every call in an
overlay its own: `HandlerRapidSpin` (`src/ov167/move_handlers.c`) calls `func_ov169_06898cf4` three times and is
followed by three identical veneers. `mwldarm` does this only for a file listed after its `-overlaygroup` and `-overlay`
options, which must be how the SDK's response file places each overlay's objects; any other file shares one veneer per
target with every call in range, even across overlays at the same address. dsd since v0.12.1-dsi.4 writes `objects.txt`
this way, while the LCF still places the objects. Before, a file that called the same far target twice, such as
`camera_system.c`, couldn't be completed. NitroWiFi's Thumb code in the LTD autoload (`.ltdmain`) gives every call its
own veneer too, as an overlay does, while dsd lists the module's objects with ARM9 main's: `tools/build/ltd_objects.py`
moves them to the end of the linker's object list, after `-overlaygroup LTD_AUTOLOAD_0,0` and `-overlay LTD_AUTOLOAD_0`,
which gives `wcm_dsi.c`'s 56 calls of `WcmSetPhase` their 56 veneers. TwlSDK's `.ltdmain` objects share one veneer per
target, across files, as main's do: `card_hash.c`'s six calls of `OS_DisableInterrupts` go through one veneer, which
`mi_ndma.c`, `mi_ndma_gxcommand.c`, `mi_sharedWram_twl.c` and `pm_twl.c` call too, so the tool leaves the objects of
`lib/twl/` with main's.

DS Protect's `dsprot_detect.c` (overlay 165) and `dsprot_detect_multi.c` (overlay 337) also retain legacy
ARM-to-Thumb veneers, eight and sixteen. The normal ARM946E linker replaces those calls with BLX and drops 96 and
192 bytes. When a compiled copy is linked, `tools/build/restore_dsprot_veneers.py` runs a private ARMv4T prelink
using the current real object list and effective LCF, once per file, each run reading the object list the previous
one wrote. It retains only that file's generated instructions, gives their pointers
ABS32 relocations to the actual Thumb SDK symbols, and redirects the compiler's call relocations
to generated local symbols. The normal ARM946E final link uses the derived objects; objdiff uses
the unchanged compiler objects. No source-function bytes, sizes or data are replaced.

This is a representation of genuine linker-generated code, of a library that was linked apart from the game: no
setting of the game's link gives these veneers alone. Compiling `dsprot_detect.c` for `v4t`, `arm7tdmi` or `v5t`
(under dsi/1.1p1, dsi/1.2 or 2.0/sp2) emits no veneer and leaves the object's ELF flags as they are, so the linker
has no per-object architecture to follow; linking the whole program as `v4t` gives these eight and 0x120 bytes of
others, for the overlay's Thumb calls of ARM code; and a `-partial` link of the object alone gives none, since it
doesn't know that its targets are Thumb. DS Protect's object evidently came already linked against the SDK as
ARMv4T code, as a vendor's library can, and the prelink reproduces that. The helper has no ROM input or fixed game
addresses. It discovers addresses on every prelink, including `--shift` builds, and requires
contiguous generated fragments, real Thumb mappings and each file's count of veneers. Unsupported ELF metadata,
unexpected layouts and linker diagnostics fail with an error. Modified code that changes these
invariants needs a new layout audit; do not change the count merely to bypass the check.

## Shifting

A mod that changes code sizes moves everything after the change, so it only works if every pointer to code or data
that moves is a relocation; a pointer that dsd left as a plain number keeps the old address. The matching build can't
show this, since nothing moves. Two tools check it:

- `tools/decomp/unrelocated_pointers.py` lists the words in the main module and the overlays that point into code or
  data that moves without a relocation. Those that point at a symbol are likely pointers; `--list MODULE` shows them
  and `--all` the rest, which are mostly byte tables that happen to look like addresses. A real one gets a relocation
  with `config_fixes.py add-reloc`, such as a pointer into an overlay that dsd couldn't attribute among the overlays
  at that address.
- `python3 configure.py --shift 0x100` pads the code by that many bytes (`tools/build/shift_lcf.py`): in main
  before Game Freak's library, which moves the rest of main and every overlay, and at the start of each overlay's
  code. The ROMs then don't match, and are tested by playing them. Run `configure.py` without it to go back.

The words that point at a symbol have all been judged: six in literal pools were real pointers and got relocations,
and the others, in literal pools and data alike, are constants or byte and halfword tables that happen to look like
addresses, such as `0x02020100`. The words that point at no symbol (`--all`) are mostly such tables too.

## Known gaps

dsd's analysis and linking have no known gaps left in this ROM.
