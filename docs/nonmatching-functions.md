# Nonmatching functions

Every function that is in C but doesn't compile to the original. The addresses are Black 2's and White 2's.
`tools/decomp/compiler_probe.py FILE --version b2_us` (and `w2_us`) shows the difference of each function in a file,
and `--show-diff 1.1p1` the instructions.

## In C, not matching

These functions are written as the closest natural C found. Unless a row says the full ROM matches, their files are
partial (no `complete` in `delinks.txt`), so the original code is linked until they match. The differences are the same
in both versions.

## Matching, but not linkable as is

- `lib/dwc/src/qr2/qr2regkeys.c` (overlay 11) matches both its functions in both versions, but its `.data` doesn't: MWCC
  lays out the key names with a heap sort by size of the reverse of their definitions, and among the strings of
  7 bytes the ROM's order (`score_`, `team_t`, `skill_`, `region`) is one that the sort gives only with one more
  initialized object of up to 4 bytes defined after the names, which the ROM's `.data` and `.bss` don't have room for:
  most likely the later SDK's `qr2_internal_key_list`, whose code the linker stripped. The file stays incomplete.
  A 4-byte `static int` defined after the names gives the ROM's order of all 33 strings, but adds its word to the
  shared section (1020 bytes against the ROM's 1016), and nothing that is listed in the sort emits no bytes: a
  `static const` scalar, read or not, is folded and not listed, and an unread static or static table is kept under
  `-ipa function` and dropped and not listed under `-ipa file` (which changes nothing else here). The ROM has no room
  for the word: overlay 11's `.rodata` ends at 0x021851c0 with qr2.c's 6 bytes and their 2 bytes of padding, and its
  `.bss` runs from qr2.c's straight into sb_server.c's.

- `lib/dwc/src/auth/dwc_profanity.c` (overlay 11), DWC's profanity check, matches its 6 functions in both versions,
  and with `-ipa file` its `.data` up to the strings of `DWCi_CheckProfanityAsync`, but the ROM has 4 zero bytes between
  `"/ac"` and `"/pr"` that nothing references: most likely a literal `""` of code that the linker stripped, which MWCC
  lays out only for a function it emits. The file stays incomplete.

- `lib/nitro/src/syscall/secure_area.c` (ARM9 main), NitroSDK's system call library at `0x02004000` to `0x02004800`,
  matches its 18 BIOS stubs in both versions, but it can't be linked: Nintendo builds the library for each game, with
  the stubs at their own places among filler bytes (in another order in each version), and the filler is the base
  ROM's, which the file doesn't write. MWCC also starts each function at a multiple of 4 bytes, where 11 of the stubs in
  Black 2 and 7 in White 2 start 2 bytes past one, and its assembler has `dcb` and `dcd` but no way to give a function
  a second entry point. The file stays incomplete.

- `lib/nitro/src/init/crt0.c` (ARM9 main), NitroSDK's startup code, matches all its functions in both versions, but
  its module parameters (`BuildInfo` and `LtdModuleParams`, in `.text`) hold the addresses of the static and LTD
  modules' autoload lists, which the build writes after each module. dsd's linker script has no symbols for them
  (its relocations from `BuildInfo` point into `.bss`, at `g_GFLSndHeap` + 0x948 and + 0x988), and the LTD module's
  words have no relocations at all, with its compressed end differing between the versions (`0x02421c40` /
  `0x02421c38`). The file stays incomplete until the linker script gives those symbols.

## Keeping this list current

After changing a source file, run `compiler_probe.py` on it for both versions, and add, update or remove its rows. A file
gets `complete` in both versions' `delinks.txt` only when all its functions match and its data is written. The report at
`build/b2_us/report.json` helps find candidates, but its fuzzy match can be below 100 for a matching function because of
relocations, and misses some differences, so the probe decides. `tools/decomp/check_nonmatching_rows.py`, which CI's
Standards workflow runs, checks that each row's functions are defined in its file and are symbols of that file's module
at the row's Black 2 and White 2 addresses; `--fix` corrects a White 2 address that has one answer.
