# Nonmatching functions

Every function that is in C but doesn't compile to the original. The addresses are Black 2's and White 2's.
`tools/decomp/compiler_probe.py FILE --version b2_us` (and `w2_us`) shows the difference of each function in a file,
and `--show-diff 1.1p1` the instructions.

## In C, not matching

These functions are written as the closest natural C found. Unless a row says the full ROM matches, their files are
partial (no `complete` in `delinks.txt`), so the original code is linked until they match. The differences are the same
in both versions.

| `src/gfl/arc_tool.c` | `ArchiveMoveImageTop` | `0x0204a870` / `0x0204a89c` | Four bytes longer in the original, 9 aligned lines off: after the entry read it reloads the spilled image offset (sp+8), adds 8 to it in place and stores it back (`ldr`, `adds #8`, `str`), then adds `entry.start`. Ours, `fimgOffset += NARC_FIMG_DATA_OFFSET + entry.start` with `fntbOffset` declared before `fimgOffset`, computes the sum in place in the original's slots but adds the 8 to the loaded `entry.start` and skips the store. Any spelling that adds 8 to the sum alone (`+= 8` then `+= entry.start`, `fimgOffset + 8 + entry.start`, `offset += ...`) lets MWCC move the sum down to that copy (16 to 22 lines). Game Freak's style (zero-initialized offset locals, chained tops, the seek written image + 8 + start + offset, top and bottom locals) gives 20 to 33 lines; the asm reads the entry with one 8-byte read, so it isn't two `u32` reads. Before that round: Four bytes longer in the original: it computes `fntbOffset + value` right after the read into its spill slot `sp+8`, and adds 8 to that slot (`ldr`, `adds #8`, `str`) just before the final seek. Written as `fimgOffset = fntbOffset + value; ... fimgOffset += 8`, ours is 4 bytes short: Thumb's `adds rd, #8` overwrites its source, so MWCC copies the sum first, and (at -O1 and up, whatever the pragmas) it then redoes the three-register add into that copy and drops the sum, which leaves `fntbOffset` and the loaded `value` spilled across the read instead. A second use of the sum that isn't a copy (`fimgOffset + 4` in a call, an assert), `+ 7` (the three-operand immediate form), or a `*`, `\ |`, `(u16)` or 64-bit sum each keep it in place, but the original shows none of them. `imageTop = fntbOffset + value + NARC_FIMG_DATA_OFFSET`, with `fntbOffset` declared before `imageTop`, gets the size and both spill slots right but applies the +8 at the definition: 29 bytes. Tried: the widths and signedness of every local (`u32`, `s32`, `long`, `unsigned long`); `+=`, `sizeof`, `8 + x`, `x = x + 8`, operand orders and groupings; `x = a; x += b`; chained and copy assignments; one reused offset variable (`fntbOffset`, `fatbOffset`, `value`, `pos`); accumulating into `fimgOffset` or `offset`; inline helpers for the size read, the sum and the final seek; block-scoped reads; zero-initialized locals; struct or array locals (a memory struct of the offsets stores in place but is 4 bytes short, 28 lines); a `const` local; same-size casts; declaration orders; the opt_propagation, opt_common_subs, opt_lifetimes and opt_strength_reduction pragmas, -O levels and -ipa modes; every mwccarm version. decomp-permuter's `value & 0xFFFFFFFFFFFFFFFFu` (a 64-bit round trip) computes the sum in place but swaps the two spill slots, and is not plausible source. Also tried: all 256 combinations of `u32`, `unsigned long`, `s32` and `long` for `value` and the three offsets, and `long` prototypes of `FS_SeekFile` and `FS_ReadFile` (all byte-identical); `8UL`, an enum constant, or an enum-typed local for the 8 (the local keeps the sum in place but holds the 8 in a register, 14 lines); `const` parameters and `register`; pointer locals for `value`, the entry and the FATB header (21 to 29 lines); `fimgOffset = fntbOffset + value; fimgOffset += 8;` both before the read (the +8 sinks to its use and the sum with it); the FATB entry's position in `fntbOffset` or a `pos` local; `fatbOffset += 12 + fileId * 8` (31 lines); and the opt_dead_assignments, opt_dead_code, peephole, scheduling, register_coloring, optimize_for_size, global_optimizer and opt_loop_invariants pragmas. Also tried: `fntbOffset` reused for the FATB entry's position, the +8 between the entry seek and the read or inside the seek, an explicit `fatbOffset += NARC_FATB_ENTRIES_OFFSET` and an inline taking `u32 *imageTop` for the final seek (22 lines each); `offset += fimgOffset + NARC_FIMG_DATA_OFFSET + entry.start` or `fimgOffset = fimgOffset + 8 + entry.start` (16 lines, still 4 bytes short with the sum moved down); `fimgOffset = fatbOffset + fatb.size + value` (32 lines, `fatb.size` is loaded again). Minimal functions move the sum the same way at `optimization_level 1` and with `opt_lifetimes` or `opt_propagation` off, and keep it in place only for a subtraction, a use of the sum that is not a copy, a conditional +8 or an operand redefined on one path (docs/matching.md, "whose only use is the copy"), none of which the original shows. Twins: none. Only `arc_tool.c` reads a NARC through FS (the other `FS_SeekFile` callers are `file_util.c`'s `GFL_ArcSysReadRawResource`, NNS SndArc and ov181's multiboot code), and no function in the ROM spills a three-register sum across a call and then adds an immediate to it in its slot. Also tried: `GFL_ArcToolInit`'s own `fntbSize` local for the FNTB read (35 lines, both values read into `sp+0x10`); `(fimgOffset += 8)` inside the seek (19 lines); the `size == 0` block before the seek (32 lines); `offset += fimgOffset + entry.start` after its own `fimgOffset += NARC_FIMG_DATA_OFFSET` (16 lines, the sum moved down); inlines taking a pointer for the sum or the +8 (moved down as in the plain form); and a local struct of the offsets with a member's address read, held in memory, which gives the in-place `adds #8`/`str` but drops the `fntbOffset` reload and moves every slot (without the address taken it is split into the baseline's scalars). Also tried: `ATTRIBUTE_ALIGN(4)` on `value`, `entry`, `fatb`, the offsets or all three, and 32 on `value` (0xb8 with 21 lines, only because `fatb.fileCount` is loaded twice, as with opt_common_subs off; the sum still moves); `volatile fimgOffset` (diagnostic: in place but reloaded, 19 lines); `entry.start + fimgOffset + offset` (17 lines, 0xb4); `fimgOffset = value; fimgOffset += fntbOffset;`, `+= 4; += 4` and the final sum's operand orders; peephole, scheduling and register_coloring off with the other pass pragmas, alone and together. The move is a back-end propagation of an `add` whose only use is the copy that Thumb's two-operand `adds rd, #8` needs: with one operand loaded from memory (the address-taken `value`), `-`, `+ 7`, `\|` and `*` updates keep the sum in place and only an immediate in the two-operand form moves it. The `add r0, sp, #0x10` base of the `fileCount` read is the lowest memory local, and an address-taken or `volatile` `fimgOffset` moves it to sp+0xc, so the original's `fimgOffset` is a spilled register variable, not a memory local. Also tried, with the alignment lever: `ATTRIBUTE_ALIGN(4)` on `NarcFATBHeader`'s `size` or `fileCount` or on `NarcFATBEntry`'s `start` or `end`, in both placements, or 8 or 32 on the locals `entry`, `fatb` and `value`: each gives 0xb8 with 21 lines (`fatb.fileCount` loaded again for the assert, the sum still moved down); 8 and 32 on the members change the structs' layout. `int fimgOffset`, `u16 fimgOffset`, `value + fntbOffset` and an uninitialized `value` do not move the sum back (0xb4, 0xc0, 0xb0). No variable holds a value set for an enum type. BW1's version (another decomp), which accumulates the image offset in the FNTB offset's variable and adds the 8 inside the last seek's argument, is 4 bytes short here too. The copy and re-add come from a back-end pass, on at `optimization_level` 1 and up and off at 0, with no limit of distance or count, that runs only for the copy Thumb's two-operand `adds rd, #8` needs: `+300` or a shift keeps the sum in place, and dead uses of the sum are removed before it. Storing the sum to an address-taken local stops it: `value += fntbOffset; fimgOffset = value;`, with `fntbOffset` declared first, gives the original's size, spill slots and in-place `+8` (7 lines off), but it adds a store the original lacks, so it is not kept. A field read's base register is always the lowest memory local, so the original's sp+8 and sp+0xc are spilled register variables. Also tried, none closer: Diamond and Pearl's reader shape (another decomp), `fimgOffset + 8 + entry.start + offset` (22 lines), a struct of the three offsets (28 lines), the `+8` folded into `entry.start`/`entry.end` (0xc0), `-= -8`, and every dsi compiler at -O4,p, -O4,s, -O3,p and -O2,p (always 0xb4). No other three-register sum kept across a call before an immediate add is in the ROM. Stand-ins under the maintainer's 2026-10-25 ruling (`volatile` on one local, a cast of an operand or array to its own type; 10 to 30 placements) don't match either: volatile on a spilled variable moves it among the memory locals' slots and reloads it, and the casts compile alike. Also tried (2026-10-26): 26 variants using distinct native `int`/`unsigned int` and SDK-long locals or own-static parameters, separate offset updates, and a grouped NARC read-header record in all six member orders. All remain 0xb4; the closest retains the same 9 aligned differing lines. The original's second store to the image-offset spill slot is never read again. No variant is retained. |

## Keeping this list current

After changing a source file, run `compiler_probe.py` on it for both versions, and add, update or remove its rows. A file
gets `complete` in both versions' `delinks.txt` only when all its functions match and its data is written. The report at
`build/b2_us/report.json` helps find candidates, but its fuzzy match can be below 100 for a matching function because of
relocations, and misses some differences, so the probe decides. `tools/decomp/check_nonmatching_rows.py`, which CI's
Standards workflow runs, checks that each row's functions are defined in its file and are symbols of that file's module
(or of the LTD autoload, for a file with migrated LTD sections, `docs/configs.md`) at the row's Black 2 and White 2
addresses; `--fix` corrects a White 2 address that has one answer.
