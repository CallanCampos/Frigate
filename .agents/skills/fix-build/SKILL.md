name: fix-build
description: Diagnose a pokebw2 build failure or compiler warning after a C or config change. Covers link errors, section ranges, module or SHA1 failures, runtime helpers, redeclarations, and probes that match while Ninja fails. Use whenever Ninja fails, warns, or a ROM no longer matches.

# Fix the build

Keep the full Ninja output and inspect every `warning:` and `error:` line; use the tail for the failing task's context.
Ninja checks, per version, the archives built from source,
every module (`dsd check modules`) and the ROM's SHA1, so the failing check names the module and the version.

| Symptom | Cause and fix |
| --- | --- |
| MWCC emits a warning while Ninja succeeds | Treat the build as unfinished. Correct the declaration, cast, initialization or duplicate definition at the reported line; do not silence warnings with compiler flags. Recompile the affected file in both versions and check the ROMs. If the first build log was incremental, run a clean build once to catch warnings in untouched files. |
| `Last symbol 'X' ... not contained within the file's section range` | A `.data`/`.rodata`/`.bss` range in `delinks.txt` ends before the file's last object. Extend the range to the end of that object. If the object is the next file's, the boundary is wrong. When an object nothing references sits between files, `config_fixes.py add-data` gives it a symbol. Fix both versions. |
| `Check ... overlay N: checksum failed` in one module the change didn't touch | (1) A function made `static` that this module calls links to address 0 through a veneer, and one whose address it loads (a `kind:load` relocation, such as ov036's pointer to `ListMenuCore_FreeStrBufs`) becomes 0. Make it global again; `mark_complete.py` and `add_source_file.py` without `--incomplete` check for this. (2) A header type change altered a caller's code in another file. `git diff include/` and probe the files that include it. A caller's local typed only to fit a wrong prototype (a `u32 heapId` passed to a parameter that is really `HeapID`) changes with it: give the local the parameter's real type. Other modules failing at the same time may only be calling into the changed one. (3) An ambiguous relocation now resolves to another overlay's symbol (see below). (4) A literal in that module that dsd took for a pointer into the data just made complete, such as ov011's MD5 constant `0x021ac7f4` that fell inside overlay 298's rodata in White 2: the same value in both versions while the data moved shows it is not a pointer. `config_fixes.py remove-reloc` it. |
| A file just marked complete fails its own overlay's check, and the overlay's `*_TEXT_END` in `build/<version>/arm9.o.xMAP` is 0x10 past `delinks.txt` | A function the file made `static` is still called from the overlay's code that is not in C yet. `mark_complete.py` only looks at other modules, so it passes; the call links to a veneer to address 1 at the end of `.text`. Find the calls with a `bl` scan of the built overlay for that address and make the function global, as `key_system_net.c`'s `KeySystemNet_GetRequest`, which data_convert_flow.c calls. |
| Fails in one version only | White 2: functions marked `different` in `build/version_map.tsv` need `#ifdef WHITE2` code. Probe with `--version w2_us`. Data that differs (message IDs, tables) can also break only one version. Compare the configs of both versions for the file. |
| Probe matches every function but the module check fails | The probe skips relocated bytes: a call to the wrong function (a call into an autoload goes through a veneer linked into the caller's `.text`, `ldr pc, =target`, so a wrong callee is one word there: `ctvt_camera.c` called `CAMERA_I2CSizeEx` where the ROM's veneer holds `CAMERA_I2CEffectExCore`), a wrong addend (an index folded into a literal pool address), the wrong runtime helper (`_s32_div_f` against `_u32_div_f`), data placed in the wrong section (`const` or not), or wrong data contents. A string literal with the wrong text, or a second copy of a string the ROM stores once (two callbacks sharing one message), changes `.data`'s size, so every later pointer moves and ARM9 main and many overlays fail at once (`gsUdpEngine.c`'s ping callback carried its own copies of the received callback's two messages); compare each section's strings with the delinked object's in `build/<version>/delinks/`. Relink both versions before calling a failure single-version: `ninja -n` shows a pending `Linking build/<version>/arm9.o` when one version's result is stale. An incomplete file's data was never compared at all, so marking one complete can surface old content errors: `demo3d_data.c` carried two swapped `VERSION_*` bytes in `sDemo3D05_Cmds` until it first linked, and its static data can be sorted in another order (`tools/decomp/rodata_order.py`): two equal local initializers swapped change only the pool words that point at them, as in `ctvt_game_cam.c`. Run `.venv/bin/python tools/build/romdiff.py extract/... build/...` for the region, or compare the built overlay in `build/<version>/build` with the original (`cmp -l` names the exact bytes, in octal). |
| ARM9 main and every module that points into it fail at once after a main file goes complete, with `arm9.bin` a few bytes short or long | The file defines a function out of address order (the probe compares each function wherever it is, but the link follows the source) or lacks data its range holds. In `build/<version>/arm9.o.xMAP` the first symbol whose address differs from `symbols.txt` names the place: `clact.c` defined `func_0204cb8c` after `func_0204cc54`, and `wm_icon.c` lacked an assert's text. Put the function in address order, or leave the file incomplete with a note. |
| A module that reads a main file's variable (the ITCM, say) fails after the file goes complete, the pointer now 0 | The file defines the variable `static`, and `mark_complete.py` checks only static functions. Make it global and declare it in the owner header, as `clact.c`'s `g_ClActSys`, which the ITCM reads. |
| `undefined:` a runtime helper (`_fadd`, `_ll_udiv`) when a file goes complete | MWCC calls the runtime's helpers by their own names, which `fp_fastI.s`'s routines carry. A helper that the compiler calls by two names gets the second as a label in `fp_fastI.s` (`_ll_mul` on `_ull_mul`). A helper that is a second entry point inside another gets its name on dsd's `.L_` label there: `_ll_sdiv` is `0x0208d414`, 0x10 into `_ll_mod`, which the original's `blx` targets. |
| `undefined: SDK_*` when a NitroSDK file goes complete | A linker symbol of the SDK's that its code reads as a number, such as a stack size, which dsd's linker script doesn't define. Read its value from the pool word (no relocation) in both versions and add it to `config/linker_symbols.toml` (`docs/configs.md`, "Linker symbols"). The probe masks relocated words, so only the link shows a symbol in the wrong pool slot. |
| An ambiguous relocation (`module:overlays(36,214)`) | dsd couldn't tell which overlay is meant, and the build links to the first. `config_fixes.py reloc-module overlays/ovNNN 'overlay(M)' ADDR`. This only links while the symbol is global. When you make a function static, check `relocs.txt` of both versions for relocations to it with several candidates; `mark_complete.py` doesn't catch these. The veneer the linker adds grows the calling overlay's `.text` by 0x10, which moves every overlay placed `AFTER` it and main's pointers into them, so most modules fail at once: ov011's call to ov189's `0x021a303c`, `overlays(165,189)`, broke everything when `status_rcv.c` made its function there static. Find the overlay whose `*_TEXT_END` in `build/<version>/arm9.o.xMAP` is past its `delinks.txt` end. |
| A literal that is an overlay ID | `OVERLAY_ID(n)` in the C, and `config_fixes.py overlay-id overlays/ovNNN n ADDR`. |
| A field referenced through its own symbol | dsd made a symbol inside a struct or table. Retarget its relocations to the base plus an addend with `config_fixes.py reloc-addend . 0xN FROM...` (the `from:` addresses of its relocations), then `config_fixes.py remove-symbol . ADDR`; both record the fix in `config/fixes.txt` for every version. wipe.c's `sWipe` had eight such symbols. |
| `redeclared` or `conflicting types` | One declaration per function, in the owner's header. Make the parameter types match the asm and update the callers. NitroSDK/NNS types live in `lib/nitro/include/nitro` and `lib/nnsys/include/nnsys`. |
| The probe calls a function "unknown" | The static's symbol still has its `func_` name. Rename it to its C name. |
| A file with a large `.bss` object goes complete, and words elsewhere (main's tables, overlays' literal pools) come out 0 | dsd took constants that happen to fall in the object's address range for pointers, and gave them symbols inside it, which the complete file no longer defines. `snd_sys.c`'s 0x9d000-byte sound heap (`0x0209e278`–`0x0213b278`) caught about 100, such as ov268's `0x020b0903`. List the relocations from other code into the range, `config_fixes.py remove-reloc` the constants, and `reloc-addend` the real pointers onto the object (the two addresses in `BuildInfo` at `0x02004fb0` became `g_GFLSndHeap + 0x948` and `+ 0x988`), then `remove-symbol` the symbols those pointed to. |
| A first build in a new worktree fails on the extract | Link `orig/`, `tools/dsd`, `tools/objdiff-cli`, `tools/wibo` and `tools/sjiswrap.exe` from the main checkout, then run `ninja`. |
| CI reaches the final ROM checks, then the build step exits 1 with no Ninja error | The log command may have failed: on a clean checkout, `tee build/ninja.log` cannot create the file until `build/` exists, and `pipefail` reports that failure. Run `mkdir -p build` before capturing Ninja output, and print the log tail on failure. |
| DS Protect veneer generation cannot decode its private `.o.xMAP` as UTF-8 | MWLD's closure report can contain garbage before the linker-command-file symbols. The private prelink needs only the layout map: use `-map unused` there, keeping the final link's options and strict decoding. Relinks of both versions produce eight veneers with no diagnostics; Black 2's ELF sections are unchanged. |
| macOS Ninja stops with exit 139 and a single `tools/wibo ... Segmentation fault: 11` compiler command | The pinned wibo can crash intermittently: earlier clean macOS runs compiled the same source and reached the ROM checks. Retry Ninja on exit 139 with the incremental build; preserve the combined log so warnings from every attempt remain visible. Limit parallel jobs if crashes recur. |
| `ninja: warning: premature end of file` | Another session is writing `.ninja_log`. Harmless. |

After a fix, run `ninja` again until both versions pass, then go back to `finish-file`. When a failure teaches
something new, add it to this table (see `record-lesson`).
